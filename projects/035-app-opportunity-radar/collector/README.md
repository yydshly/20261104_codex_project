# App 增长雷达

每天保存 Apple 公开榜单及产品资料，观察哪些产品和方向出现排名提升、新入榜、评分新增与评分暴涨。覆盖中国、美国、日本、英国 App Store，以及美国、日本、英国 Google Play 免费榜与付费榜，各最多 100 条。产品和方向均支持平台筛选，排名与评分增量只使用同平台历史。

## 看报告

双击 `reports/latest.html`，或运行 `打开报告.cmd`。报告可离线使用，支持平台、市场、名称、方向、具体场景、核心能力和增长信号的组合筛选。新增“场景与能力”页签，标签汇总可点击下钻到成员产品。`reports/latest.md` 是文字摘要，`latest.json` 可供后续分析程序或 AI 读取。报告只使用实际观测，首日明确显示“正在建立增长基线”。

也可以运行 `python preview.py`，在浏览器打开 `http://127.0.0.1:5227/`。这个只读预览服务仅提供当前 HTML 报告；每天报告更新后刷新页面即可。2026-11-15 已在浏览器实测搜索、四区筛选、组合筛选、空结果、增长信号与分页；验收记录和截图保存在 `reports/ui-check/`。

## 运行

需要 Python 3.10 或以上，以及 Node.js。安卓解析依赖通过 npm ci --ignore-scripts 安装（版本锁定于 package-lock.json）；Python 无第三方依赖。在本项目目录运行：

```powershell
python -m app_radar collect
python -m app_radar status
python -m app_radar report
python -m unittest discover -s tests -v
```

也可从任意目录运行：

```powershell
python "F:\codex_project1\20261104_codex_project\app-growth-radar\run.py" collect
```

`collect` 退出码 0 表示完整成功，2 表示部分缺失或采集失败，1 表示配置或运行错误。每批请求间至少间隔 3.2 秒，瞬时网络错误会有限重试。采集需要电脑联网；Codex 工具的网络沙箱可能需要正常的联网权限。保留证书验证，不使用私人登录态。

每日执行由本聊天的 Codex 自动化安排在北京时间 09:00。电脑和 Codex 的可运行状态、网络及任务权限会影响实际执行。手动运行与每日任务使用同一个命令；同一时刻只允许一个采集进程，进程异常退出后操作系统会释放锁。

## 保存什么

- `data/radar.sqlite3`：逐日产品快照、地区榜单、采集结果与错误。
- `data/raw/日期/地区/`：每次真实响应及来源 URL、采集时间、SHA-256，失败前取得的原始响应也保留。
- `reports/日期.html / .json / .md`：每日报告；同日重跑更新当天报告和 `latest`。
- `data/logs/`：可选的 `run.ps1` 日志入口所保存的终端日志；该入口仅在本机允许运行 PowerShell 脚本时使用，无须为它更改执行策略。日常使用上面的 Python 命令即可。

同日重跑以最新成功榜单更新榜单成员，不追加重复名次；失败重试保留当天之前已取得的有效观测。当天有效的评分数不会被后续缺失字段抹除。离榜 App 默认继续追踪 30 天，每区最多刷新 1000 个（当日榜单产品始终保留），超过上限会在质量说明中列出。系统不自动删除历史、迁移其他资料库或清理磁盘。

## 增长判断

| 指标 | 条件 |
| --- | --- |
| 排名上升 | 与昨天同地区、同榜单的成功观测比较 |
| 新入榜 | 昨天完整榜单未出现、今天成功榜单出现；首次收录不能判为新入榜 |
| 新增评分 | 同一地区连续两日的累计评分数之差；缺失或评分数回退时留空 |
| 评分暴涨 | 当天新增至少 20，达到前 7 天日均的 3 倍；需要 9 个连续日期的完整观测，基线须大于零 |
| 方向增长 | 在同一地区和方向内按 App ID 去重，统计样本量、可比较量、排名上升和评分增长的产品数 |

所有日期按北京时间计算。没有历史不补造数据，缺日不补零、也不把多日增量冒充单日增量。Apple 榜单是来源发布时刻的快照，源更新时间和本地观测时间分别记录；源更新时间早于 36 小时或明显晚于当前时刻时不作为今天的有效榜单。

方向规则在 `directions.json`：优先使用 `overrides` 内的 App ID 人工指定，其次匹配名称关键词，未命中则使用商店分类。名称匹配是初步归类，可能误分；报告始终显示分类说明，规则修改后可运行 `report` 重新分类当前比较窗口。

## 范围与限制

这是榜单样本监测，不能代表全量 App 市场。已接入 iOS 和 Google Play；不包含畅销榜、全分类榜、广告库、真实下载量、活跃用户和收入。评分新增和排名只作增长信号；机器人评分、商店数据修正及更新延迟都可能影响信号。

更多分类榜、手动关注名单和付费第三方数据可以后续通过独立数据适配器扩展。收入估算需要可靠校准数据，当前版本不输出收入数字。

## 官方数据来源

- [Apple RSS 美国免费榜真实端点](https://rss.marketingtools.apple.com/api/v2/us/apps/top-free/100/apps.json)
- [Apple ID Lookup 官方说明](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/LookupExamples.html)
- [Apple Search API 参数与请求频率说明](https://performance-partners.apple.com/search-api)

数据来源为 Apple。程序只保留分析所需的元数据，不下载应用安装包、图标或预览媒体。

## 安卓数据口径

Google Play 使用 google-play-scraper 解析公开商店榜单和详情。保存的是解析结果、商店链接、观测时间及哈希；来源没有提供榜单更新时间时保持为空。解析库不是 Google 官方API，商店页面改版可能导致失败；错误会保留在报告中。详见 https://github.com/facundoolano/google-play-scraper 。

安卓评分可能是全球汇总，同一 App 的不同国家页面不能相加为新增用户。排名按所在市场比较，评分变化按同平台同市场连续观测计算，作为商店信号。安卓ID使用 play:包名，榜单使用 android- 前缀，与现有 iOS ID、历史记录互不覆盖。跨平台同名产品不自动合并。

可使用 python -m app_radar collect --android-only 仅刷新安卓并保留报告内已有的 iOS 观测。每日9点任务运行普通 collect，一并刷新两平台。Android 首日单独建立基线。

## 场景与核心能力标签（2026-11-20）

`directions.json` 同时维护 `taxonomy_version`、`tag_overrides` 和 `tag_rules`。场景回答“用户在什么情况下用”，能力回答“产品具体做什么”；每个产品可以拥有多个标签。优先使用以平台独立 App ID 为键的商店说明核对项，记录来源链接、核对日期和限制；其余名称规则标记“待复核”，支持 `exclude` 排除歧义名称。宽泛商店分类不自动生成能力，未匹配产品保留“待补充”。商店说明核对代表核对开发者声明，不代表实测功能或增长归因。

HTML 产品表显示标签、依据与说明，可同时筛选场景和能力，搜索也包含标签。场景与能力页签支持平台、市场、标签类型、最少样本、关键词与排序；默认至少3个样本，选择“全部”可查看单产品线索。点击标签自动带入同平台、同市场的产品筛选。

JSON 新增 `tag_growth`、`tag_coverage`，每个产品新增 `scenes`、`capabilities`、`tag_evidence`、`tag_status`、`tag_note`。聚合限定同平台同市场，每个标签内按 App ID 去重，多标签分组不能相加。排名上升率使用实际连续两日同榜排名可比产品为分母（离榜、新入榜、只有评分可比的样本不放入分母）；新入榜和评分增长分别列出。少于5个样本标记小样本，不解释为行业趋势，也不按国家合计安卓评分。

规则调整后运行 `python -m app_radar report` 即可用已有观测重建当前报告，不需重新联网采集或迁移数据库。分类版本保存在报告中；规则变化本身不计为市场增长。历史日的旧报告保留，除非明确指定 `report --date YYYY-MM-DD` 重建该日。标签覆盖率与待补充数量始终显示，避免将有标签样本当成全量市场。

验证：`python -m unittest discover -s tests -v`，`node tests/report-dom.mjs`，`node tests/tags-dom.mjs`。后两项运行真实报告的 DOM 与事件逻辑，不替代浏览器视觉验收。

## 用户评论与产品机会研究（2026-11-22）

`collect` 在榜单采集后自动运行评论研究。首版按增长信号和持续跟踪名单每平台选择最多6个 App，同一平台 App 只取一个市场；保留原来的平台独立身份。`config.json` 的 `reviews` 控制启用、数量、90天分析窗口和跟踪名单；评论每 App 最多100条，Apple 按最新排序最多2页，Google Play 使用已锁定版本的最新排序接口。1—2星作为差评线索，4—5星作为需求理解线索，3星单独保留。中文、日文、英文按市场请求；Google 的页面地区与语言不保证作者所在地。

可单独运行 `python -m app_radar research` 刷新评论，复用最新增长快照。报告分别标出增长观测日期和评论采集日期；禁止用 `--date` 冒充历史评论采集。`report` 只读取已有证据重建报告，不重复联网抓取。定时任务继续每天北京时间09:00运行一次 `collect`。

新增 SQLite 表 `research_runs`、`review_observations`、`review_fetches`，以增量建表方式保存评论逐日观测与请求状态，不改变原有增长表。评论原始响应继续按来源、观测时间和 SHA-256 归档至 `data/raw/日期/地区/reviews-ios` 或 `reviews-android`。评论 ID、正文重复、编辑版本、评分和发布时间用于去重及回查；不收集评论者头像或建立用户画像。失败保留已取得证据，空样本与解析/联网错误明确区分。

`research_rules.json` 维护中英日主题匹配、排除词、最小原型、验证动作和实施约束。规则聚类是待复核研究线索，不是完整语义理解，也不证明增长原因。未匹配的低星评论仍可在“评论证据”查看。每个痛点至少两条评论ID与正文不同的低星评论才生成机会假设；一次个案只列证据。好评主题与低星痛点分开；候选按主题证据量排列，顺序不代表市场规模或创业成功率。

HTML 新增“需求与机会”页签（可用 `latest.html#research` 打开），支持平台、市场、产品、需求/痛点关键词筛选，评论证据支持星级与分页。逐产品显示样本日期范围、低星/高星数量、来源状态与归类线索；假设卡片显示最小原型、验证动作和约束。原文仅展示短摘录，并链接来源；完整研究证据留存在本地原始响应和数据库。来源评论可能被编辑或删除，需结合归档复核；旧版本差评不证明当前版本仍有缺陷。

JSON 新增 `research`（研究范围、日期、规则版本、逐产品需求/痛点、候选机会、证据与来源状态）；Markdown 增加研究摘要。采样不是全量或随机样本，不能将样本差评比例解释为总体不满意率，不能把评论数当成评分总数、用户数或收入。

检查：`python -m unittest discover -s tests -q`、`node tests/research-dom.mjs`。主题精度和产品切入仍需人工复核、实际复现、用户访谈与付费意愿验证。

功能请求也从高星评论提取，单独标记“功能请求（不限星级）”，避免漏掉“满意但希望改进”的需求。报告中的“本轮切入判断”来自按原文逐条阅读的研究记录，与规则候选分开。记录保存为 `reports/research-briefs-评论采集日期.json`；只有 App、市场和所有证据ID仍匹配本轮有效样本的完整记录才载入，避免错用其他平台、地区或过期证据。日期变化后不会自动冒用前一日判断，日常研究任务会结合当日样本更新。
