# 手机动作驱动小柚的首轮实验

原片确实展示了真人源片、灰色人体网格与写实换角输出之间的动作及视角对照。对小柚，先用 4 至 6 秒真人源片加已确认角色图做同机位换角基线；需要修动作或换机位时，再加入三维动捕与 Pose 控制。当前已核对原片关键画面和技术文档，未逐帧量测、安装模型或生成样片。本机只读检测为 RTX 4070 Laptop、约 8GB 显存，候选换角工作流没有提供这台 Windows 笔记本上的已验证运行结果。

## 原帖明确给出的内容

[William 的原帖](https://x.com/dlkfzwilliam2/status/2119250763704889433)依次提到 RGBMoCap、骨骼重定向、MiniMax H3 和 Character-Swap-LoRA，并引用 [OJI3 的演示](https://x.com/OJI3_NIKKE/status/2119161807038550342)。本次通过 FxTwitter 镜像读取完整文字，ID 与引用关系保存在 [来源记录](sources/01.json)，并在 X 官方嵌入播放器中核对了演示的五个取样时点。尚未核对原作者完整工程及回复中的技术细节。

原帖对自动修复滑步、动作稳定和外观重建的表述是流程概述，没有附可直接运行的节点图、LoRA 发布者、精确版本或失败样本。不能由这段文字推定每一步已经自动接通。

## 原片可见的三路对照

在官方播放器实际播放并定位 0.087、2.177、4.877、10.059 和 20.075 秒时，左侧为固定室内白衣真人的前视源片，中央为带有 Person1 标识的灰色人体网格，右侧为灰外套、蓝裙的写实女性输出。多个取样时点的手臂与躯干动作有可辨对应。中央和右侧出现俯视、侧向和背向观察角度时，左侧仍保持前视。

这支持“演示展示了动作与不同视角的三路对照”。画面没有直接披露中间文件、相机与骨架如何解算、模型版本和实际生成步骤，不能据此证明每一步自动完成或动作完全准确。脸在画面中较小，且转头、侧向和背向较多；单条约 20 秒的演示不能证明多镜头身份稳定、嘴形准确或实时交互。

## 四种材料分别负责什么

| 材料 | 表达内容 | 需要的转换或核查 |
| --- | --- | --- |
| 手机源视频 | 原始动作、表情、相机、背景与光照 | 检查遮挡、出画、动作时序及镜头变化 |
| FBX 或 BVH | 骨架、关节运动与根节点运动 | 在三维工具中检查骨架映射、比例和接触；不能直接充当 H3 参考视频 |
| Pose 或 Depth 视频 | 逐帧姿态或空间结构 | 使用匹配的控制模型、预处理、分辨率和帧数 |
| 小柚参考图 | 五官、头发、衣服和目标外观 | 与镜头景别匹配，先确认脸部与身体信息足够 |

LoRA 是加载进主模型的适配权重。公开换角工作流将源视频、角色图和适配权重一起用于生成；不应机械理解成“先用 H3 输出一条成片，再把成片交给独立 LoRA 程序加工”。公开的通用换角适配器也不意味着必须先训练小柚专属 LoRA。

## 候选实现与证据范围

- [RGB MoCap](https://github.com/toyxyz/toyxyz_RGBMocap)：Windows 图形应用，集成多种人体重建模型，提供接触修正、重定向和导出。不同模型能力、许可与资源要求分别核对。低显存观察只对应特定模型与测试，不能用来估算 H3 显存。
- [MiniMax H3](https://github.com/MiniMax-AI/MiniMax-H3#model-variants-and-input-specifications)：FL2VA 对应文字及首尾帧任务，Ref2VA 接收图像、视频及音频参考；官方输入规格没有声明直接接收 FBX/BVH 骨骼。参考视频生成不等于逐帧 Pose ControlNet 约束。
- [Akatz Character Swap LoRA](https://huggingface.co/akatz-ai/MiniMax-H3-Character-Swap-LoRA)：可核查的候选换角实现，使用源表演视频和角色图。模型卡推荐 V1.5，仍明确保留身份、时间、遮挡及剪切处漂移等实验性限制。它与原帖只给出的通用名称匹配，但发布者尚未与原演示对上。
- [H3 Fun ControlNet Union 2.0](https://huggingface.co/alibaba-pai/MiniMax-H3-Fun-Controlnet-Union-2.0)：这是叠加在 H3 基座上的额外结构控制分支，Pose 使用 DWPose 骨架视频，Depth 使用深度图视频，示例输入参数为 `control_video`。不能仅因同为 H3 就认定可以直接插进任意换角节点图。2.0 需要对应的配置和加载器，模型卡明确警告沿用旧配置可能静默产生错误结果。

上述项目文档快照和获取时间见 [references/index.json](references/index.json)。没有读取或执行远程仓库中的安装脚本。

## 原帖省略的连接环节

RGB MoCap 的骨骼输出不包含一条完整的影视表演。[用户指南](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md)说明，重定向写入映射的身体、手指骨骼，毛发与衣物物理不模拟；体型比例差异较大时，手脚仍可能需要在动画软件中继续编辑。因此，原帖的“自动修复”和“姿态锁死”不能替代动作验收。骨骼路线也不会自动提供可供换角模型照搬的眼神和脸部表情。

RGB MoCap 的 `Export Preview` 输出是左侧原视频加右侧三维视窗的并排画面，并且保留当前视窗叠加层。这适合检查动捕结果，不应未经处理就喂给 H3 当正式参考片。应导出 FBX 或 Blender 工程，建立单独的干净相机画面，再渲染所需参考或控制视频。Blender 工程中的源视频只是视窗相机背景，并不自动成为最终渲染背景。[导出说明](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md#preview-video)

换角的输入也有两层含义：源视频提供运动和场景线索，小柚图提供外观。先检查人物选择与遮罩，才能知道换的是谁。候选实现输出整幅生成画面，并非把生成的人物按遮罩无损贴回原背景；因此“保留背景”仍是生成目标，需要检查结果。[H3 Relay 工具说明](https://github.com/akatz-ai/h3-relay/blob/main/example_workflows/toolkit/README.md)

## 候选换角工作流的实际门槛

[Akatz 配套示例](https://huggingface.co/akatz-ai/MiniMax-H3-Character-Swap-LoRA/blob/main/examples/README.md)和 [H3 Relay 工具包](https://github.com/akatz-ai/h3-relay/blob/main/example_workflows/toolkit/README.md)给出的是一个可审查的候选：H3 Ref2VA INT8、编码器、音视频 VAE、SAM 人物遮罩，再加载 Character Swap V1.5 与独立 Turbo8 两个适配器。两者强度均为 1，示例采用 8 步、CFG 1、`er_sde` 与 `normal`。这些是候选的起始配方，不是原帖已经披露的参数。

作者验证的运行环境是固定 ComfyUI 提交与前端、PyTorch/CUDA 组合以及 Linux/RTX 4090。示例指出，24GB 显卡全驻留也会耗尽显存，正常卸载模式才完成该配置；最低 schema 版本不等于所有相同或更新版本、Windows 环境都已验证。当前本机显存约 8GB，不能从这份文档推定可以直接运行。先确定一个与相同模型及适配器兼容的推理环境，再决定本地低显存方案或其他可用算力，不急于下载整套权重。

此外，源视频准备会统一到 24fps 并对齐尺寸，换角规划器负责分段和历史帧处理。[实际 API 图](https://huggingface.co/akatz-ai/MiniMax-H3-Character-Swap-LoRA/blob/main/examples/H3-Character-Swap-Relay-V2.api.json)默认有独立窗口设置。不要把 Fun ControlNet 模型卡的帧数公式直接套成所有换角流程的源片时长限制。正式记录应同时保留源片长度、实际采样窗口和最终交付长度。

## 路线 A 先验证换角

输入为一段约 4 至 6 秒、固定机位、单人的上半身视频，以及一张已确认的小柚参考图。拍摄或选择的动作只包含“抬右手、挥手两次、放下”，手尽量不遮脸。最终采样窗口与交付帧数按选用工作流的规划规则记录，不把另一条 ControlNet 路线的帧数公式直接套入。

可动手准备的材料包括：已获授权的真人源片、用户确认的小柚参考图、五个动作事件的时间标记，以及能加载指定基座和适配器的推理环境。参考图中应能清楚辨认脸型、五官、发型和服装；本轮始终使用同一文件，避免把改角色图引入对照。每次实验保存输入校验值、工作流与节点版本、模型版本、种子、采样窗口、输出时长、耗时和实际费用。

约 5 秒的拍摄脚本如下。时间段是本项目给拍摄者的编排，实际事件以源片为准，不是模型已经承诺的执行精度：

| 时间 | 动作 |
| --- | --- |
| 0.00 至 0.75 秒 | 面向相机，双手自然放下，保持中立 |
| 0.75 至 1.50 秒 | 抬起右手到肩部附近，不遮脸 |
| 1.50 至 3.50 秒 | 匀速挥手两次，身体保持朝前 |
| 3.50 至 4.50 秒 | 放下右手 |
| 4.50 至 5.00 秒 | 回到中立并短暂停留 |

先使用候选实现附带的工作流，记录实际的 H3 基座、LoRA、节点版本和输入文件。保留源视频声音或先只检查画面，避免同轮增加配音变量。当前只是实验方案，没有提交生成请求。

可采用的动作要求如下。这是用于本次实验的提示词草案，并非原作者提示词：

> 将源视频中选定人物替换成参考图里的小柚。保持参考角色的脸型、头发和服装。按源视频的顺序抬起右手、挥手两次并放下，保持源视频相机及背景，不增加人物、道具或镜头。

先各做一个简单源片与一个转头或手部近脸的困难源片。小样通过后，再对同一困难片段做两次独立生成，观察是否容易复现。单个成功样本只能证明该次可行，不能估算稳定成功率。

## 路线 B 再增加动作资产控制

只有当路线 A 的动作跟随不足，或需要改变体型、接触与三维机位时，才增加以下环节：

1. 用选定的 RGB MoCap 引擎重建短片动作。
2. 对照原片检查右手与左手、动作顺序、身体比例和接触状态；必要时手工修正。
3. 将动作重定向到目标三维资产；没有可用骨架资产时，先用中性人体做动作预演。
4. 渲染匹配帧数和画幅的参考视频，或生成对应 Pose、Depth 控制视频。
5. 分别验证外观参考和结构控制，再评估二者是否有可兼容的组合工作流。

FBX 负责可编辑动作，控制视频负责喂给生成模型。姿态控制与身份保持是两项独立验收，不因姿态准确就自动算脸部一致。

## 首轮验收

以下数值是本项目的首轮试验标准，可以根据样本调整，不是模型保证或原演示已经达到的成绩。当前没有小柚样片，尚未打分。先固定相机、角色图、声音和调色，只测动作与身份。

| 项目 | 观察方式 | 首轮通过条件 |
| --- | --- | --- |
| 动作顺序 | 源片与结果同步对看 | 右手抬起、挥动两次、放下的顺序完整，无左右互换 |
| 时序跟随 | 标记开始抬手、抬到位、两次挥动极值及放回中立五个事件 | 不预先伸缩时间轴；暂以每事件绝对偏差不超过 0.25 秒为筛选门槛，24fps 约 6 帧，保留各自测量值 |
| 脸部身份 | 开头、抬到位、两次挥动之间、放手和结束五处人工核对 | 脸型、五官、发型、服装和身体比例五处都无可见换人；抽样通过不代表全片或多镜头身份保证 |
| 遮挡恢复 | 在后续困难片段中另测手靠近或经过脸部 | 手离开后恢复同一角色，不残留错位五官；简单基线不据此声称已经通过 |
| 时间连续性 | 正常速度完整播放，再逐帧检查短片 | 首轮目标为零处明显的脸部、手部或服饰突变，问题按帧号记录 |
| 背景与相机 | 选择三个固定地标，在起点、中点和终点共九处核对 | 没有新增或消失的地标；布局明显漂移则标记复核，不能用背景稳定替代身份判断 |

动作时间、身份取样和连续性分别记录，不合成一个没有依据的“稳定率”。保留可复看的帧，而非只填写“相似”；嘴形、音频同步和端到端延迟不纳入本轮通过结论。

## 和后续条目的连接

第 02 条解决该镜头选哪张角色卡；第 03 条补齐角色参考资产；第 04 条在身份与运动通过后统一输出色彩。第 08 条与本条共享动捕候选，第 10 条可辅助整理镜头报告。
